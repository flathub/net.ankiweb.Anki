# Updating the Anki version

How to move this package from one Anki release to the next (e.g. 26.05 → 26.08).

## The automated way

When a stable Anki release is published, Anki's `sync-release.yml` workflow runs
`scripts/update-anki.py` and uploads the result as a patch artifact. The script does
steps 1–4, 6 and 7 below. The workflow has no write access to this repo. It comments on
Anki's release PR (the one that merges the release branch into `main`) with a report and
the commands that apply the patch here and open the PR.

You can also run the script locally (needs `uv`, `git` and the KDE SDK from the
prerequisites):

```shell
uv run scripts/update-anki.py 26.08
```

It exits with status 2 if something needs a manual fix (a patch that does not apply, a
metainfo validation error). The report's "Needs attention" section lists the problems. Use
the steps below to fix them on the branch, then build and test (step 8) before you merge.

The rest of this file describes each step, for when the script fails or you need to do a
step by hand.

## Why this is not a one-line bump

Flatpak builds run offline: `OFFLINE_BUILD=1`, `YARN_ENABLE_NETWORK=0`, `UV_OFFLINE=1`.
Nothing the build needs may be fetched during `flatpak-builder`. Anki pulls dependencies
from three separate ecosystems, so every one of them has to be re-vendored into a
lockfile-shaped JSON **before** the build can see it:

| Ecosystem   | Upstream lockfile | Vendored into          | Generated by                        |
|-------------|-------------------|------------------------|-------------------------------------|
| Rust        | `Cargo.lock`      | `cargo-sources.json`   | `scripts/generate-cargo-sources.py` |
| Node / yarn | `yarn.lock`       | `yarn-sources.json`    | `flatpak-node-generator`            |
| Python      | `requirements.in` | `python3-modules.json` | `scripts/generate-py-sources.sh`    |

The Python side is different from the other two: it does **not** read an upstream lockfile.
`requirements.in` is a mirror of Anki's runtime dependencies, taken from the pyproject
files (see step 4).

On top of that, the manifest pins several build tools by exact version and checksum
(`yarn.cjs`, `protoc`, `uv`, `maturin`, the hatchling build-constraint wheels). A new Anki
release can require newer ones.

## What a bump actually touches

The size of the change depends on the kind of release.

- **Point release** (25.09.3 → 25.09.4): often just the git `tag` / `commit` in the manifest
  plus the metainfo entry. See `a8784be`.
- **Feature release** (25.09.x → 26.05): all three vendored source files, patch refresh,
  build-tool pins, metainfo. See `4833e7e`.

Do not assume which one you have — run the regeneration steps and let the diffs be empty
if nothing changed.

## Prerequisites

Working `flatpak-builder` with the KDE 6.11 SDK/Platform and the `rust-stable` / `node24`
SDK extensions installed, plus `git`, `python3` (3.11+, for `tomllib`), `uv`, and a
checkout of Flathub's generator tools.

```shell
# from the repo root
git clone https://github.com/flatpak/flatpak-builder-tools
git clone https://github.com/ankitects/anki
```

Install the node generator (needed for step 3):

```shell
pipx install ./flatpak-builder-tools/node   # provides `flatpak-node-generator`
```

## Step 1 — pick the release and pin it

Find the tag and its commit:

```shell
git -C anki fetch --tags
git -C anki rev-list -n 1 26.08     # -> the commit sha to pin
```

Update the `anki` git source in `net.ankiweb.Anki.yaml` (around line 263):

```yaml
      - type: git
        url: https://github.com/ankitects/anki.git
        tag: '26.08'
        commit: <sha from above>
```

Then check out that exact tag locally — every generator below reads from this checkout:

```shell
git -C anki checkout 26.08
```

Quote the tag. Bare `26.05` is fine in YAML but `26.10` would parse as a float and lose
the trailing zero.

## Step 2 — regenerate the Rust sources

```shell
python3 scripts/generate-cargo-sources.py anki/Cargo.lock cargo-sources.json
```

This needs network access: for every `git+` dependency in the lockfile (currently
`ankitects/linkcheck` and `ankitects/rust-url`) it clones the repo to a temp dir to find
the crate's `Cargo.toml` and inlines it. If it raises `packages not found in <url>@<rev>`,
a git dependency moved or was renamed upstream — that needs a look, not a retry.

It also writes the vendoring `cargo/config` as an inline source at the end of the JSON.

## Step 3 — regenerate the Node sources

```shell
flatpak-node-generator yarn anki/yarn.lock -o yarn-sources.json
```

There is no committed wrapper script for this one, so double-check the result rather than
trusting the command: every entry must have a `dest` under `flatpak-node/`, and the file
must still contain the `flatpak-yarn.js` plugin entry — the manifest imports that plugin
explicitly (`./yarn.cjs plugin import .../flatpak-node/flatpak-yarn.js`) and the build
fails without it.

The generator has special handling for esbuild and Playwright binaries, which is why
`yarn-sources.json` contains Chromium/Firefox archive entries. Those are large and make
this by far the biggest diff in a bump; that is expected.

**Also check the yarn version.** The manifest downloads a specific yarn CLI:

```yaml
      - type: file
        url: https://raw.githubusercontent.com/yarnpkg/berry/refs/tags/%40yarnpkg/cli/4.9.2/packages/yarnpkg-cli/bin/yarn.js
```

Compare `4.9.2` against the `packageManager` field in the new `anki/package.json`. If
upstream moved, bump the URL and recompute the `sha256`. (The manifest strips
`packageManager` from `package.json` at build time, so a mismatch will not error loudly —
it will just build with the wrong yarn.)

## Step 4 — regenerate the Python modules

First reconcile `requirements.in` with upstream. The file is grouped by Anki component:

```
# anki (pylib)   -> anki/pylib/pyproject.toml   [project] dependencies
# aqt            -> anki/qt/pyproject.toml      [project] dependencies
```

Diff those two dependency lists against `requirements.in` and add/remove/adjust bounds to
match. PyQt itself is **not** listed — it comes from the PyQt BaseApp, not from pip.
`update-anki.py` writes this file for you: it copies both lists, and drops PyQt, duplicates
and dependencies whose markers exclude Linux.

Then:

```shell
./scripts/generate-py-sources.sh
```

which does two things:

1. `uv pip compile` resolves `requirements.in` into the pinned, hashed
   `python-requirements.txt` (gitignored — it is an intermediate).
2. `flatpak-pip-generator.py` turns that into `python3-modules.json`.

Two flags in that script matter:

- `--runtime=org.kde.Sdk//<version>` is read from `runtime-version` in the manifest, and
  that SDK must be installed.
- `--python-version 3.13` must match the Python in the runtime.
- `--prefer-wheels=rpds-py,orjson,markupsafe` forces prebuilt wheels for packages whose
  source builds need network or a Rust toolchain we do not want to run there. If a new
  dependency fails to build offline for the same reason, add it to this list.

## Step 5 — refresh the uv build constraints

Anki's wheel build runs `uv build` with `--build-constraint /run/build/anki/uv-constraints.txt`
(added by `python-build-fixes.patch`), because offline uv cannot resolve its own PEP 517
backend. The manifest therefore carries two things that must agree:

1. the inline `uv-constraints.txt` source listing local wheel filenames, and
2. a `type: file` source for each of those wheels.

```yaml
      - type: inline
        contents: |
          hatchling @ ./hatchling-1.30.1-py3-none-any.whl
          ...
        dest-filename: uv-constraints.txt
```

If a wheel is bumped (by hand or by the checker, see below), the filename in the inline
block must be edited to match or the build fails with an unresolvable constraint.

## Step 6 — re-check the patches

Six patches are applied to the Anki tree:

| Patch                          | Purpose                                              |
|--------------------------------|------------------------------------------------------|
| `no-update-check.patch`        | disable the in-app updater (Flathub manages updates) |
| `desktop-file-name.patch`      | set the desktop file name to `net.ankiweb.Anki`      |
| `strip-python-formatter.patch` | drop the `ruff format` call from codegen             |
| `strip-mpv-ytdl.patch`         | drop `--no-ytdl` (yt-dlp is not bundled)             |
| `python-build-fixes.patch`     | drop mypy protoc plugin; add the uv build-constraint |
| `yarn-4-fixes.patch`           | offline yarn: no corepack, use `ANKI_YARN_BINARY`    |

These are context-sensitive `git apply` patches, so they break on unrelated upstream edits
near the same lines. Test them before a full build:

```shell
git -C anki apply --check ../no-update-check.patch ../strip-python-formatter.patch \
  ../python-build-fixes.patch ../desktop-file-name.patch ../yarn-4-fixes.patch \
  ../strip-mpv-ytdl.patch
```

To refresh one: apply what still applies, edit the file by hand, and regenerate with
`git -C anki diff -- <path>`. `strip-mpv-ytdl.patch` needed exactly this in the 26.05 bump.

If upstream fixes something a patch works around, delete the patch and drop it from the
`paths:` list.

## Step 7 — update the metainfo

`net.ankiweb.Anki.metainfo.xml` keeps a single `<release>` entry for the shipped version.
Replace it with the new version, the upstream release date, and a link to the GitHub release:

```xml
  <releases>
    <release version="26.08" date="2026-08-01">
      <url type="details">https://github.com/ankitects/anki/releases/tag/26.08</url>
    </release>
  </releases>
```

Notes:

- Use `appstreamcli validate net.ankiweb.Anki.metainfo.xml` to validate the file (or let the Flathub build-bot run
  it on the PR).
- Watch for a stray release entry with a PyPI-looking version such as `2026.6.1.19` — the
  data checker has inserted one before (fixed in `0fe6588`). Delete it.

## Step 8 — build and test

```shell
./compile-app.sh                 # flatpak-builder --repo=./repo build-dir ... --force-clean --ccache
flatpak build-bundle ./repo anki.flatpak net.ankiweb.Anki
flatpak install --user ./anki.flatpak
flatpak run net.ankiweb.Anki
```

Worth exercising after a bump, since these are the parts the packaging touches:

- app launches and the icon/name resolve (the desktop-file-name patch)
- audio/video playback works (bundled mpv)
- **Help → About** shows the new version
- **Tools → Check for Updates** does nothing (the no-update-check patch)
- LaTeX rendering, if `org.freedesktop.Sdk.Extension.texlive//25.08` is installed
- syncing (needs `--share=network`)

## Step 9 — commit

Follow the existing convention: one commit named after the version (`update to 26.05`), on
a branch named for the version, opened as a PR against `master` so Flathub's buildbot
builds it. The generated JSON files are committed as-is; do not hand-edit them.

## Updating everything else

The non-Anki modules (mpv, libplacebo, libass, rsync, protoc, uv, maturin, and the
constraint wheels) all carry `x-checker-data`, but Flathub's update bot is **disabled** for
this repo via `flathub.json` (`disable-external-data-checker: true`). Since January 2026
the maintainer runs the checker manually instead:

```shell
flatpak run --filesystem=$PWD org.flathub.flatpak-external-data-checker --update \
  net.ankiweb.Anki.yaml
```

That produces the `Update rsync, maturin-bin, uv-bin, ...` style commits in the log. Run it
as a separate commit from the Anki bump, and re-check step 5 afterwards if it touched any
of the hatchling/packaging/pathspec/pluggy/trove-classifiers wheels.

Bumping the Qt runtime is a third, independent change (`7863171`): it touches
`runtime-version`, `base-version`, the `texlive` extension version and the node SDK
extension. Then regenerate `python3-modules.json` (step 4) against the new SDK.
